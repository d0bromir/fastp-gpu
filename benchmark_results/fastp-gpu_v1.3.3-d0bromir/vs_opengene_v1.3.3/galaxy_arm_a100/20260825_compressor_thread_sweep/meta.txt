What this run set is:
  Motivated by JCB Reviewer 2's Comment/Question 3 ("Why cap compressor
  threads at [the manuscript's stated] 4?"), which had already surfaced a
  real manuscript inaccuracy independent of this sweep: the described
  min(w,4) fixed cap no longer matches the shipped code, which now uses a
  fairness-based processorThreads/mainWriters allocation. That correction
  was made from git design history alone (see reply-to-reviewer-2.md,
  Comment 3). An external collaborator review (Prof. Simeonov) suggested
  the design-history answer would be stronger backed by an actual
  measurement across compressor-thread counts; this is that measurement.

  reads_out (passed-filter read count, 717,214,748) was identical across
  all six runs, confirming correctness was unaffected by the compressor-
  thread count at either extreme (1 or 32).

Result: wall-clock time (external process timing around each run):

    compressors   wall (s)    speedup vs. 1 thread
    1             1085.02     1.00x
    2              544.93     1.99x
    4              274.81     3.95x
    8              233.04     4.66x
    16             233.58     4.65x
    32             234.38     4.63x

  Speedup is near-linear from 1 to 4 threads (1.99x, 3.95x -- essentially
  matching the thread count), diminishes sharply by 8 threads (4.66x, well
  short of 8x), then is flat from 8 through 32 (within 0.6%, no directional
  trend) as some other pipeline stage (I/O, decompression, CPU trim/stat --
  not measured further here) becomes the bottleneck instead of compression.

Interpretation for R2 Comment 3 / the "Parallel output compression"
  paragraph: this validates both directions of the actual design-history
  answer. The old fixed cap of 4 compressor threads left real throughput on
  the table relative to 8 threads (4.66x achievable vs. 3.95x at the old
  cap point, a ~15% opportunity cost). The current w/M-proportional
  allocation does not need an explicit further cap either -- other stages
  saturate before compressor-thread count becomes the bottleneck again, so
  scaling indefinitely past ~8 threads would not have helped further even
  without any cap at all.
