What this run set is:
  A follow-up to two earlier investigations that both tested FASTP_GPU_SLOTS
  (default 8 vs. max 32) but never together with a *working* T=64: the
  original slots sweep (../..): only tested T=16; the thread-ceiling
  collapse investigation (../20260823_thread_ceiling_investigation/) tested
  slots at T=64 but *before* the PACK_IN_MEM_LIMIT fix, when the pipeline
  was CPU-starved regardless of slot count -- so neither could show whether
  slot count matters once the GPU is actually being fed at high -w. This run
  set closes that gap: FASTP_GPU_SLOTS 8 vs. 32, at T=32 and at T=64, on the
  post-fix build, with 1Hz nvidia-smi utilization sampling on both GPUs
  (dual-GPU mode is active throughout) -- the post-fix runs in the prior
  investigation recorded wall time and correctness only, no utilization.

Result: slot count makes no measurable difference at either thread count.
Wall time: 235s (T32/s8) vs 237s (T32/s32); 239s (T64/s8) vs 241s (T64/s32)
-- all four within run-to-run noise of each other and of the T=32 baseline
already reported in the paper (234s). GPU utilization: 26-27% average, 30-31%
peak, on both GPUs, in all four configurations -- flat regardless of slots
or thread count. This extends the existing "GPU utilisation does not respond
to slot count" finding (originally T=16 only) to T=32 and, for the first
time with a working pipeline, T=64 -- further corroborating the CPU-side
batch-packing bottleneck as the true ceiling (see
sec:limits:pack in the manuscript), not a new finding.

Correctness: all four runs produced identical passed-filter read counts
(717,214,748), matching every other run in both prior investigations on this
dataset.
