What this run set is:
  An investigation triggered by a routine GPU-SM/warp-utilisation check
  ("does raising -w or FASTP_GPU_SLOTS increase GPU utilisation?"), which led to
  testing the tool's actual thread ceiling (-w is hard-capped at 64) for the
  first time -- the paper's main benchmark suite had only gone up to T=32.
  At T=64, WGS_PE_40G collapsed to ~16x the T=32 wall time (3,969s vs 245s),
  with GPU utilisation falling to 1.6% (from 26.5% at T=32).

  Three explanations were ruled out directly rather than by inspection alone:
  GPU slot pool size (FASTP_GPU_SLOTS 8 vs 32: t64s8v3 vs t64s32, identical
  3,969s), compressor thread count (FASTP_COMPRESSORS=8: t64fc, no material
  change), and NUMA topology (this node is single-socket / single-NUMA-node,
  not applicable, no dedicated run needed). A live gdb thread backtrace of the
  stalled process (not machine-capturable as a file; see the paper's
  Limitations text / reply-to-reviewer-1.md for the transcript excerpt) showed
  the great majority of worker threads parked in usleep() inside
  PairEndProcessor::processorTask, polling their own round-robin-fed input
  queue on a 100us cycle with no backpressure or work-stealing -- i.e. worker
  starvation, not GPU contention.

  Root cause: src/common.h's PACK_IN_MEM_LIMIT (=64) bounds the number of
  in-flight packs *globally*, shared across all -w round-robin-fed per-worker
  queues rather than per-worker. That gives each worker only
  PACK_IN_MEM_LIMIT/threads packs of buffering headroom on average --
  comfortable at threads=8 (8 packs/worker), tight at 32 (2/worker), and at
  64, barely more than 1 pack/worker: the reader can never build a lead over
  consumption, forcing near-lockstep handoff and collapsing the pipeline's
  overlap.

  Fix (this commit's source changes, also in the accompanying src/ sync):
    - src/common.h: packInMemLimit(threads) = max(PACK_IN_MEM_LIMIT, threads*4),
      applied at the throttle sites in peprocessor.cpp / seprocessor.cpp in
      place of the bare PACK_IN_MEM_LIMIT constant. Unchanged at threads<=16
      (max(64, threads*4) == 64), so memory footprint at the thread counts the
      constant was originally tuned for is untouched.
    - src/singleproducersingleconsumerlist.h: replaced the usleep(100)-based
      polling wait in the consumer with a condition-variable-based blocking
      wait (waitForData()), notified from produce()/setProducerFinished().
      Secondary fix: reduces wake/sleep churn at high -w; verified NOT to be
      the primary fix by itself (an earlier attempt with only this change
      still showed a multi-thousand-second trajectory at T=64).

  Result: T=64 CPU 3,969s -> 238s (t64fix2), T=64 GPU >3,600s (timed out
  before completing, pre-fix) -> 240s (t64gpufix), both now matching T=32
  (234s CPU / 236s GPU-build-at-T=32). T=32 itself shows no regression from
  the fix (234s vs the original paper baseline of 241.289s, within
  run-to-run noise). T=8 spot-checked post-fix (564s) to confirm the fix is
  a no-op there, as packInMemLimit(8) == PACK_IN_MEM_LIMIT == 64 by
  construction.

  Correctness: every run in this set (pre-fix and post-fix, CPU and GPU,
  every thread count and every rule-out configuration) produced identical
  read counts -- 722,563,222 reads in, 717,214,748 reads out after filtering
  -- confirming the collapse and its fix are purely a throughput/liveness
  issue, never a correctness issue.
