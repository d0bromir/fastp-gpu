# NVIDIA Parabricks on ARM Neoverse-N1: Compatibility Evidence

**Purpose.** This document is the supporting evidence for our reply to Reviewer 1,
who asked:

> *"There is not enough comparison with the state-of-the-art work. For example,
> NVIDIA Parabricks uses GPUs for accelerating heavy short-read, how does the
> proposed algorithms compare with it in performance?"*

It records, in reproducible detail, why a head-to-head Parabricks benchmark could
not be executed on our evaluation platform, and what we verified in order to rule
out a mis-configuration on our side.

**Date of experiments:** 2026-08-16
**Generated by:** `pb_test.sh`, `pb_forensic.sh`, `isa_scan.sh` (listed in §10)

---

## 1. Summary of findings

1. NVIDIA Parabricks publishes **33 container tags**; **23 are `amd64`-only**.
   Only **10 tags have an `arm64` image**.
2. **All 10 `arm64` images fail on our host** with `SIGILL` (illegal instruction)
   when executed on real data — including Parabricks' own error handler reporting
   `Process terminated with signal [SIGILL: 4]`.
3. The cause is an **instruction-set mismatch**, not a configuration error. The
   `arm64` images are built for NVIDIA **Grace (Neoverse-V2, ARMv9-A)**. Our host
   is **Ampere Altra (Neoverse-N1, ARMv8.2-A)**. The binaries use at least two
   feature sets absent on N1:
   - **SVE** (Scalable Vector Extension) — e.g. `cntb`, `whilelo`, `ld1d`, `ptrue`
   - **FEAT_LRCPC2** (ARMv8.4 unscaled acquire/release) — e.g. `stlurb`
4. There is **no runtime fallback**: the affected objects contain **zero**
   `getauxval`/HWCAP references and **zero** IFUNC (`IRELATIVE`) relocations, so
   the code paths are unconditional rather than CPU-dispatched.
5. Parabricks is **closed-source**, so it cannot be rebuilt for ARMv8.2-A.
6. This is a **platform limitation only**. It is *not* evidence about Parabricks'
   performance, and it does *not* imply any defect in Parabricks. On `x86_64` or
   on Grace-based ARM hosts the software is expected to run normally.

### Verbatim error output

Parabricks' own error handler reports the signal (releases ≥ 4.5.0-1):

```
[PB Info] ||                 Parabricks accelerated Genomics Pipeline                 ||
[PB Info] ||                              Version 4.5.1-1                            ||
[PB Info] ||                                  bam2fq                                 ||
[PB Info] Starting traversal
Process terminated with signal [SIGILL: 4].
For technical support visit https://docs.nvidia.com/clara/index.html#parabricks
Exiting...
Could not run bam2fq
Exiting pbrun ...
```

Releases ≤ 4.4.0-1 abort at the identical point but their older `pbrun` does not
print the signal name (only `Could not run bam2fq`). For those we confirmed the
signal by invoking the underlying binary directly, which returns shell exit code
**132** (= 128 + SIGILL(4)) with `Illegal instruction (core dumped)`.

Under `gdb`:

```
Program received signal SIGILL, Illegal instruction.
0x0000aaaaaaac6368 in prepareAdapterSequences ()
=> 0xaaaaaaac6368 <_Z23prepareAdapterSequencesv+1992>:  cntb    x23
--- context ---
   0xaaaaaaac635c <_Z23prepareAdapterSequencesv+1980>:  str     xzr, [x1, #64]
   0xaaaaaaac6360 <_Z23prepareAdapterSequencesv+1984>:  ldr     x0, [sp, #120]
   0xaaaaaaac6364 <_Z23prepareAdapterSequencesv+1988>:  mov     x22, #0x0
```

`cntb` (*Set scalar to multiple of predicate constraint element count*) is an
**SVE** instruction. It is not part of ARMv8.2-A and is architecturally undefined
on Neoverse-N1, hence the trap.

### Shared libraries (`/usr/local/parabricks/binaries/lib`)

| Object | SVE | LRCPC2 |
|---|---|---|
| `libbwalib.so` | 213 | 0 |
| **`libfilehandle.so`** | **580** | **63** |
| `libpairHMMlib.so` | 311 | 0 |
| `libswlib.so` | 124 | 0 |

`libfilehandle.so` is the decisive object: it is linked into **every** Parabricks
tool. This explains why tools whose own executable is clean (e.g. `bam2fq`, 0 SVE)
still trap — they inherit the unsupported code through this shared dependency.
Consequently no Parabricks tool is usable on this CPU.

Detection patterns used (GNU `grep -E` over `objdump -d` output):

```
SVE    : \bz[0-9]+\.[bhsdq]|\bp[0-9]+/[zm]\b|\b(ptrue|whilelo|whilelt|whilels|rdvl|addvl|cntb|cnth|cntw|cntd)\b
LRCPC2 : \b(ldapurb|ldapurh|ldapur|ldapursb|ldapursh|ldapursw|stlurb|stlurh|stlur)\b
i8mm   : \b(smmla|ummla|usmmla)\b
BF16   : \b(bfdot|bfmmla|bfcvt|bfcvtn)\b
SHA3   : \b(eor3|rax1|bcax|xar)\b
```

These counts are conservative lower bounds (mnemonic matching only).

## 6. Minimal reproducer

A four-line program isolates the hardware behaviour independently of Parabricks:

```c
#include <stdio.h>
#include <sys/auxv.h>
#include <asm/hwcap.h>
int main(void) {
    unsigned long hw = getauxval(AT_HWCAP);
    printf("HWCAP_SVE = %s\n", (hw & HWCAP_SVE) ? "yes" : "NO");
    __asm__ volatile("ptrue p0.b" ::: "memory");   /* one SVE instruction */
    printf("SVE instruction executed OK\n");
    return 0;
}
```

```
$ gcc -march=armv8-a+sve -o sve_probe sve_probe.c && ./sve_probe
HWCAP_SVE   = NO
HWCAP_ASIMD = yes
about to execute: ptrue p0.b
Illegal instruction (core dumped)      # exit 132
```

The CPU traps on the very first SVE instruction. This is expected and correct
behaviour for ARMv8.2-A hardware.

## 7. Controls — ruling out mis-configuration

We deliberately eliminated the obvious alternative explanations.

| Hypothesis | Test | Result |
|---|---|---|
| GPU driver broken | Repaired a pre-existing driver/kernel-module mismatch, rebooted | `nvidia-smi` reports driver 595.71.05, CUDA 13.2, both A100s visible |
| GPU not visible in container | `apptainer exec --nv … nvidia-smi` | Both A100 80GB detected inside the container |
| CUDA unusable | Parabricks `deviceQuery` (SVE-free binary) | Runs, exit 0 |
| Container/image corrupt | `pbrun version`; banner output | Correct version string; all tools print their banner and parse arguments |
| GPU code path is the problem | `pbbwa --version` after driver repair | Initialises the GPU ("GPU-PBBWA mem, Sorting Phase-I"), exit 0 |
| Failure is GPU-related | `coverage`, `collectmultiplemetrics` — CPU-only paths | Still `SIGILL`; **no GPU involvement** |
| Runtime CPU dispatch exists but mis-detects | `objdump -T`, `readelf -r` on `coverage`, `libfilehandle.so` | **0** `getauxval`/HWCAP refs, **0** `IRELATIVE` relocations → no dispatch |
| Only one bad release | All 10 `arm64` images, 2023→2026 | Identical failure in every one |

The binaries load, link, initialise the GPU, print their banners and parse
arguments correctly. They fail **only** when execution reaches vectorised compute
code. This is precisely the signature of an ISA baseline mismatch.

## 8. Why there is no workaround

- **Rebuilding is impossible.** Parabricks is proprietary and closed-source
  (NVIDIA AI Product Agreement). The only source shipped in the image is
  `third-party-source/libvgio-snapshot-20240319.tar.gz`, included for LGPL
  compliance. No Parabricks source or build system is distributed.
- **No runtime fallback exists.** Verified above: no HWCAP dispatch, no IFUNC.
- **No compatible older release.** The very first `arm64` image ever published
  (`4.2.0-1.grace`) already traps, as does the newest (`4.7.1-1`).
- **Emulation is not a scientifically meaningful option.** A binary-translation
  layer (e.g. QEMU user-mode) could emulate SVE, but it cannot pass through CUDA
  to a physical GPU, and any timing obtained under emulation would be worthless as
  a performance comparison.
- **No second machine.** The only other host available to us (`a2`, Intel Xeon
  Gold 5218, `x86_64`) has **no NVIDIA GPU**, so the `amd64` images cannot be run
  there either.

## 9. Scope, limitations, and honest interpretation

We wish to be explicit about what this evidence does and does not show.

1. **It is a statement about our hardware, not about Parabricks.** Nothing here
   suggests Parabricks is defective, slow, or poorly engineered. NVIDIA targets
   its ARM builds at Grace-based systems, which is a legitimate engineering
   decision. On `x86_64` or Grace hardware Parabricks is expected to work as
   documented.
2. **We cannot report any Parabricks performance number**, neither favourable nor
   unfavourable. Any such number would be fabricated. We therefore make no
   performance claim relative to Parabricks.
3. **The tools are not directly comparable in function.** In release `4.7.1-1`,
   the `pbrun` tool set is: `applybqsr, bam2fq, bammetrics, bamsort, bqsr, check,
   collectmultiplemetrics, dbsnp, deepsomatic, deepvariant, deepvariant_germline,
   fq2bam, fq2bam_meth, genotypegvcf, germline, giraffe, haplotypecaller,
   indexgvcf, markdup, minimap2, mutectcaller, ont_germline, pacbio_germline,
   pangenome_aware_deepvariant, pangenome_germline, postpon, prepon, rna_fq2bam,
   somatic, starfusion` (see
   [Tool Reference | parabricks docs](https://docs.nvidia.com/clara/parabricks/tool-reference)).
   There is **no standalone FASTQ quality-control /
   adapter-trimming / filtering tool** equivalent to fastp, and `pbrun fq2bam`
   exposes no adapter-trimming or quality-filtering options (we inspected the
   shipped argument definitions; the only filter option is `--filter-flag`, a SAM
   flag filter). Parabricks addresses alignment and variant calling; fastp
   addresses pre-alignment read preprocessing. A like-for-like throughput
   comparison would therefore require care even on compatible hardware.
4. **Counts in §5 are lower bounds** obtained by mnemonic matching, not by full
   instruction decoding.
5. **The single deep trap site we localised per image is the *first* one reached.**
   Given thousands of unsupported instruction sites, it is not the only one.

Suggested framing for the manuscript: report the platform incompatibility as the
reason a direct empirical comparison was not possible, cite Parabricks in the
related-work discussion on its documented merits, and avoid any implied
performance ranking.

## 10. Reproduction

Scripts used (kept on the test host under `/home/mpiuser/parabricks/`):

| Script | Purpose |
|---|---|
| `isa_scan.sh <dir>` | Disassemble every ELF in a directory and count instructions unsupported on Neoverse-N1 |
| `pb_test.sh <tag>…` | End-to-end pass/fail per image (`pbrun bam2fq` + raw-binary signal probe) |
| `pb_forensic.sh <tag>…` | Per-image forensic record: `pbrun` error, then `gdb` capture of the trapping instruction |

Minimal manual reproduction for a single image:

```bash
# 1. fetch the arm64 image
apptainer pull --arch arm64 pb.sif \
    docker://nvcr.io/nvidia/clara/clara-parabricks:4.5.1-1

# 2. confirm the GPUs are visible inside the container
apptainer exec --nv pb.sif nvidia-smi

# 3. run a real pipeline  ->  SIGILL
apptainer exec --nv -B /data:/indata -B /out:/outdata pb.sif \
    pbrun bam2fq --in-bam /indata/example.bam --out-prefix /outdata/o

# 4. locate the trapping instruction
gdb -batch -ex run -ex 'x/1i $pc' --args ./coverage --input example.bam --output cov.txt
```

**Data used:** `example.bam` from the `falco` test-data distribution (a small,
publicly available alignment file). The failure is independent of input content —
it occurs during setup/traversal, before any substantial data processing.
